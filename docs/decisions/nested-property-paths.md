# Decision record: nested property paths (issue #28)

- **Status:** ACCEPTED and BUILT (2026-10-21). Maintained summary: `CLAUDE.md` -> "Nested property paths".
- **Driver:** [issue #28](https://github.com/SmetDenis/obsidian-frontmatter-date-manager/issues/28) - "Support for Nested Properties" (reporter `fizykz`, label `enhancement`); the maintainer promised it for the next release.
- **Plugin version at time of analysis:** 1.6.0.
- **Decided by:** the maintainer, on options put to them during framing and implementation.

## 1. The request

Power users keep service properties in a group so they do not crowd the top of a note: a `meta` group holding the last-edited date, the last-opened date and the edit count. The plugin could only write top-level properties; typing something path-like into a property-name field produced one flat key with an odd name.

The issue's example showed a list under `meta` (`- updated:`, `- viewed:`, `- edits:`). The maintainer decided to solve the general case instead - nested keys addressed by a path - and not to follow the example's list form.

## 2. Options and decisions

| Fork | Options | Decision and why |
| --- | --- | --- |
| How nesting is expressed | A "nested properties" toggle that makes a dot a separator everywhere; one "put everything in a group" field; syntax in each name, always on | **Syntax in each name, no toggle.** A toggle leaves a trap (a path typed while it is off becomes a flat key with an odd name); one group field cannot keep `created` at the top and move `viewed` inside. Flat and nested names mix freely, at any depth. |
| Separator and compatibility | Dot with `\.` escaping; dot with an automatic settings migration; dot with stored names kept literal plus a hidden per-part path; `/`; `>` | **`>`, no escaping, no migration.** Dots occur in real flat keys (`app.version`, `Person.name`), so a dot without migration moves existing dates. The migration was rejected: it changes only settings, and an older plugin version on a second device would read the escaped name literally and write junk into notes. YAML forbids none of the candidates mid-key, so rarity decides: `>` cannot start an unquoted key and practically never appears in one. A dotted name stays one flat property; the settings field explains that under it. |
| Parent exists but is not a group | Skip and report; replace with a group; wrap the old value; write to a fallback place; for a list, find and update an item | **Skip that key only and report it;** the rest of the note is written. Replacing or wrapping changes data other plugins may rely on; a fallback place creates duplicates; the list form needs guessing. An empty parent (`meta:`) holds nothing and becomes a group. |
| A group or list where a date goes | Replace it; skip it - for nested names only, or for all names | **Never replaced, for all names.** The old code silently replaced a list or group at a top-level `updated`, `viewed`, the counter, and in populate's overwrite-all mode - data loss. Accepted as a deliberate behavior change for names without `>` (changelog line). |
| Two equal date names | Forbid everywhere (reset one at load); forbid in the form only; allow | **Form only.** A stored setup that writes two dates into one property (e.g. viewed and updated as "last touched") keeps loading and writing as before. Accepted price: Obsidian runs `validate` once when the settings open, so such a field now shows an error while the plugin keeps writing. |
| One name nested in another (`meta` and `meta > updated`) | - | **Refused everywhere:** the form shows an error, loading resets the longer date name to its default (repeated until none is left) and disables a colliding counter, and the write boundary drops the longer path. |
| Invalid path in the settings file (`meta >`, `> updated`) | Do not write that date and keep the text; reset to the default name; switch the date off | **Do not write it, keep the text.** It can only come from a hand edit or an older version where `>` was a plain character, synced in. It behaves like a blank name (nothing written); the manual command and bulk tools say the name is invalid, and the settings field shows the error on open. Reset-to-default would put dates where the user did not put them and lose the typed path; switching the date off hides the field and its error. |
| Moving values after a rename | A sentence in the docs; a notice with a button that opens "Rename property" prefilled; nothing | **A notice with a button** - a separate follow-up task, together with paths in "Rename property". Not built here. |
| A group shared with another property through a YAML reference (`base: &shared`, `meta: *shared`) | Copy the group before writing (copy-on-write); skip that date and report it | **Skip and report** (decided during the pre-close review). YAML anchors parse into ONE object, so a plain write would also put the date under `base`. Copying was what every Codex reviewer proposed; it was rejected because it silently turns a reference the user wrote into two independent groups. A re-review then showed that Obsidian 1.13.4 does exactly that on any write to the note (it stringifies the frontmatter with `aliasDuplicateObjects: false`, as it has for every flat date the plugin ever wrote); the skip was kept with that in view, and the docs say so. Price: such a note gets no date there until the reference is gone - removed by the user, or expanded by Obsidian when it saves another property. |
| Hash filter: a group left holding only the plugin's keys | Keep the group line in the hash (document the residual); drop it too | **Drop it.** Otherwise the plugin's first write - which creates `meta:` - adds a line to the hash, and a second device in "frontmatter"/"both" mode re-stamps once. For the same reason an empty group ON the path of a plugin key (`meta:`, `meta: {}`, `meta: null` for `meta > updated`, at every level of a deeper path) is dropped too: the first write fills it, and keeping its line would make that write look like an edit (found in the pre-release review). Price: in those two modes, adding or removing such an empty group by hand is not counted as an edit. An empty group off every plugin path stays in the hash. |
| Listing notes with an unreadable date in "Find out-of-order dates" | List them; leave them out | **Leave them out.** The tool looks for out-of-order pairs; an unreadable date is not one, and its skipped tables cover only the writes it would make. |

## 3. What was built

- **Pure path module** (`src/propertyPath.ts`): parse (`>`-split, trimmed levels, an empty level is invalid), read (`value` / `missing` / `blocked`, with a reason: a parent that is not a group, or a group shared through a YAML reference), write (create groups at the end, `meta:` becomes a group in place, refuse a blocked parent or a container target without mutating anything), conflict check, the dot-hint predicate, the hash filter's second pass, and the `PropertyTarget` / `PropertySkip` helpers every writer uses. Keys are looked up and written as own properties only: a configured name is outside input, and `__proto__ > updated` must reach the note, not `Object.prototype`.
- **One write-boundary resolution** of the four names, `propertyPaths()` in `main.ts`, used by the automatic pipeline, the last-opened stamp and the three date-writing bulk tools. Writes run through the path module on the live frontmatter inside `processFrontMatter` (the metadata cache can lag).
- **Nothing written, nothing re-serialized.** Obsidian 1.13.4 parses the frontmatter into an object, runs the callback and always stringifies the object back; only a byte-identical result skips the write, and an exception from the callback aborts before it. So a callback whose every value was refused throws (`NothingWritten` in the pipeline and the last-opened stamp, `BulkSkipped` from the bulk mutators via `writeTargetsOrSkip`): the note is not rewritten for a write that never happened, and no self-write token is recorded.
- **The out-of-order fix writes both dates or neither.** The automatic pass re-checks both paths on the live frontmatter and falls back to the ordinary values (announcing no fix) when either is refused; "Find out-of-order dates" skips such a note.
- **Reporting.** Skipped properties travel as `{ name, reason, parent? }`: the manual command lists them in its notice; automatic passes show one notice per session naming the plugin; bulk previews leave such values out of the diff and list them in a "will not be written" table; a partial refusal discovered during a run lands in a separate "were not written" table, and a note refused entirely is listed as skipped. An invalid name stops the bulk tools before the preview and is reported for the edit counter too.
- **Hash filter.** Flat names keep the original line filter byte for byte - pinned by a golden test captured from the old implementation, because any change would re-stamp every note tracked in "frontmatter"/"both" mode. Nested paths are removed by an indentation-aware second pass; other keys of the same group still count as edits. "Ignore these properties" accepts the same syntax.
- **Settings.** Validation for invalid paths, equal date names (form only) and nesting conflicts; a one-line hint under a field whose name has a dot but no `>` (it follows the typing: the 1.13 runtime re-evaluates `visible` after each control change). Descriptions of the four fields explain `>`.
- **Texts** in all 21 UI languages; README (all five translations) gains a "Nested properties" section.
- **Release level:** MINOR (new capability; no removed or renamed key, command or default), with a changelog line for the container behavior change.

## 4. Accepted residuals

- Inline groups (`meta: {updated: x}`) and quoted keys are not removed by the hash filter's second pass; their lines stay in the hash, as quoted flat keys always have. After the plugin's first write Obsidian stores the block in its usual form.
- The notation differs from Bases and Dataview (`meta > updated` in the plugin, `meta.updated` in formulas); the dot trap is closed only by the hint.
- A literal `>` cannot be part of a property name; `>` is slower to type on mobile keyboards.
- A device with an older plugin version writes a nested name as one flat key - the README asks users to update every device first.
- Obsidian's Properties panel cannot edit nested values (source mode only).
- Notes whose parent is not a group stay without that date until the user fixes the property; a note whose group is shared through a YAML reference, until the reference is gone (Obsidian expands it on the next write of any other property).
- Obsidian re-serializes the whole frontmatter on every write, expanding YAML anchors/aliases into independent copies - for flat names too, as before this change. The plugin cannot avoid that without hand-writing YAML, which the project's safety rules forbid.
