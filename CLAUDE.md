# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

Obsidian plugin that automatically maintains frontmatter date properties - `created` (on file creation), `updated` (on edit), and `viewed` (last-viewed, stamped on file open; opt-in, disabled by default) - plus an opt-in edit-activity counter (`updated_count`, disabled by default) that bumps a number on each real edit - and provides bulk tools to populate timestamps from filesystem dates, rename keys, reformat date strings, and detect/fix `updated < created` inversions across a vault.

**Target: Obsidian v1.13.0+** (`minAppVersion` in manifest.json). The floor was raised `1.11.0 -> 1.13.0` (2026-08) to adopt the 1.13 declarative settings API (`getSettingDefinitions()`, required for the new global settings search) and `ButtonComponent.setDestructive()` - Obsidian 1.13 went public on 2026-07-30 (public release 1.13.4), so these are no longer early-access APIs. Users on Obsidian 1.11-1.12 keep the last 1.2.x plugin release (fully functional) and simply stop receiving updates until they update Obsidian - nothing breaks for them. The `obsidian` dev dependency is pinned to `~1.13.1` (tilde, not caret) - the newest npm types at migration time; before using an API newer than that (e.g. the `secret` setting control `@since 1.13.2`, `SettingDefinitionBase#disabled` from 1.13.5), verify the API is in BOTH the published npm types and the current public Obsidian release. `getLanguage()` (`@since 1.8.7`) remains comfortably below the floor - see the Internationalization Key Pattern.

## Safety first (core principle)

The user's notes are irreplaceable - never corrupt, lose, or reorder note data. Every change to a vault file must be the smallest, safest mutation that achieves the goal; when a write is uncertain or unnecessary, do nothing. This invariant outranks any feature. Concretely:

- **Mutate frontmatter only through `app.fileManager.processFrontMatter()`** - never hand-write note files (no whole-file `vault.modify`, no string-replacing YAML). This preserves the body, key order, comments, and unrelated keys.
- **Touch only the configured keys.** Leave all other frontmatter and the entire note body untouched.
- **Write only on a real, detected change** - never an unconditional or no-op write. Respect the hash-gated pipeline (see Key Patterns); needless writes churn `mtime` and fight sync.
- **Never guess-and-overwrite a value you can't safely parse.** Disambiguate ambiguous input (e.g. epoch seconds-vs-ms via `epochNumberToDate`); if a date can't be parsed safely, leave it unchanged rather than corrupt it.
- **New mutation / bulk / "fix" paths are opt-in and safe-by-default:** default new fix strategies to disabled, default bulk operations to fill-missing (not overwrite), and require a mandatory dry-run preview plus a red Run button with explicit irreversibility wording for anything destructive (see Destructive operation UX).

## Obsidian API - IMPORTANT

Claude's training knowledge about the Obsidian plugin API is outdated. **Always** use context7 MCP and official Obsidian developer documentation to verify API signatures, available methods, and current patterns before writing or modifying plugin code. Do not rely on memory - check the docs. Likewise, before bumping or trusting a pinned version, verify the **currently published** versions of the `obsidian` types and `eslint-plugin-obsidianmd` (the community review linter) against npm - the review bot always runs the latest linter, so a stale local pin can let new rule violations slip through.

- `Plugin` lifecycle: `onload()`, `onunload()`
- Vault events: `app.vault.on('modify' | 'create' | 'rename' | 'delete', ...)`

## End-to-end tests (real Obsidian)

`e2e/` drives the **built** plugin inside a real Obsidian (pinned to `1.13.4`) via WebdriverIO + `wdio-obsidian-service`, covering only the seams the unit `obsidian` mock cannot reach: real `processFrontMatter` serialization (body / key order / comments / unrelated keys survive), `number`-vs-`string` on disk, self-trigger suppression on a real `mtime`, the dirty-editor-buffer write guard against Obsidian's real merge machinery (`editor-dirty-merge.e2e.ts` - the only place the `TextFileView` `dirty`/merge behaviour exists at all), the bulk-modal UI wiring (all five modals driven through real DOM clicks), and the settings "Ignore these properties" exclude UI (comma input splits into native list rows, dedup, row deletion). `excalidraw.e2e.ts` additionally drives the REAL `obsidian-excalidraw-plugin` (installed by `wdio.conf.mts` as an installed-but-DISABLED community plugin pinned to `2.26.4`; the spec enables it in `before` and disables it in `after`, so other specs are unaffected - first run downloads the release into `e2e/.obsidian-cache/`). It is the only place the drawing-aware write guard can be proven against Excalidraw's actual save/reload machinery (its > 5-min `reload(true)` + `clearDirty()` data-loss path); all Excalidraw coupling lives in `helpers/excalidraw.ts`. Pure logic is already unit-tested - never duplicate it here. Full scenario list: `e2e/README.md`.

**Settings window model (1.13):** Obsidian 1.13 opens settings in a separate OS window by default (vault config `settingsPopoutWindow`, default `true`; verified in `obsidian-1.13.4.asar`: `shouldUsePopout()` = `canPopoutWindow && getConfig("settingsPopoutWindow")`). `settingsTab.open()` in the Page Object sets that config to `false` before opening, forcing the classic in-window modal so every `$` selector, the `.modal`-scoped bulk Page Object, and the marketing-banner `activeDocument` helpers stay in the main webdriver context. Also: the settings modal keeps other tabs' DOM around, so Page Objects must only interact with **displayed** elements (a bare `$` can match a hidden element of another tab and the raw-coordinates click lands elsewhere - this bit `setting-page-back-button` first).

- **Layout:** `specs/*.e2e.ts` (Group A auto/command path, Group B the five bulk modals), `helpers/` (per-test notes / frontmatter parsing / settings patch), `pageobjects/` (ALL DOM coupling - `settingsTab`, `bulkModal`), `vaults/simple` seed (each spec file gets its own copy; tests create their own notes via `createNote`).
- **Stable-selector contract:** interactive bulk-UI controls carry `frontmatter-date-manager-*` classes (button bar + pager in `src/bulk/chrome.ts`; the mode/override/scope/strategy dropdowns; the reformat day/month order dropdown `frontmatter-date-manager-slash-order`; the rename inputs/toggle; the five Settings bulk buttons; the "Ignore these properties" exclude input + add button `frontmatter-date-manager-exclude-input`/`-add` and the native exclude list `frontmatter-date-manager-exclude-list` via its `cls:` field). Page Objects key off these classes - keep them when changing the UI (or update the PO), and add them via `addClass`/`cls:`, never `element.style`. Declarative sub-pages have no class hook (`page` definitions carry no `cls`), so the PO navigates them by visible row name (`openSubPage('...')` - e2e runs English-only) and clicks the visible `.setting-page-back-button`. **A `list` renders non-entry rows as `.setting-item` too** - its `emptyState` placeholder (`.mod-empty-state`) and its `heading` (`.setting-item-heading`) - so the exclude-list row selector excludes BOTH; forgetting the heading one silently inflates every row count by one (it broke all three `settings-exclude-list` specs when the heading was added).
- **Characterization:** specs assert existing behavior, so a fresh spec passes on its first run. A failure is a real bug/regression or an Obsidian serialization quirk - fix the root cause; never weaken the `created`/`updated`/body safety asserts.
- **Run (manual, local, pre-release - NOT in CI):** `make test-e2e` (all) or `make test-e2e-spec SPEC=<name>` (one); `make typecheck-e2e` checks specs/PO without launching Obsidian and runs in `make pre-commit`. First run downloads Obsidian to `e2e/.obsidian-cache/` (gitignored); needs a display (`xvfb-run -a` on headless). **Requires Node ≤ 22 locally:** WebdriverIO 9.x can't open a WebDriver session on Node 26 (its undici rejects the forbidden `Content-Length`/`Connection` headers `webdriver` sets - [wdio #15265](https://github.com/webdriverio/webdriverio/issues/15265)). The `test-e2e`/`test-e2e-spec` targets prepend `E2E_NODE_DIR` (default Homebrew keg-only `node@22`; override via `make test-e2e E2E_NODE_DIR=/path/to/node22/bin`) to `PATH` for the run only - your default `node` is left untouched - and abort with a hint if no Node ≤ 22 is found. **Obsidian version pin:** `browserVersion: '1.13.4'` in `wdio.conf.mts` - the public release of the 1.13 line the `obsidian` types target (`~1.13.1`) and the plugin's `minAppVersion` 1.13.0 floor; the other 1.13.x entries in the launcher catalog (1.13.0-1.13.3 and 1.13.5+) are catalyst/insider-only betas, so 1.13.4 is the one freely runnable pick. Inspect the settings tab / modals visually with `browser.saveScreenshot()` or `browser.debug()`.

## Store screenshots (marketing)

The five screenshots embedded in `README.md` (and shown on the community store) are **generated, never hand-made**, by the staged manual spec `e2e/specs/marketing-screenshots.e2e.ts` (NOT a characterization test - it stages curated notes, drives the UI to its most compelling state, overlays a benefit caption, and captures the window). Output: `screenshots/0N-*.png` at the **repo root** - tracked in git, embedded in `README.md`. Regenerate with `make screenshots`; never edit the PNGs by hand. The repo-root `screenshots/` dir must already exist (`saveScreenshot` does not create it, and e2e specs may not import node builtins - `import/no-nodejs-modules`). This is behind-the-scenes tooling: keep its specifics here, NOT in `README.md`/`e2e/README.md`.

- **Store image rules (locked - conform to these):** at most **5** screenshots; **3:2** aspect ratio, recommended **1200x800 px**; `PNG`/`JPEG`/`WebP`; **max 5 MB** each. We ship exactly **1200x800 PNG**. The spec sizes the window to `1200x800` (3:2); Obsidian renders at **retina 2x**, so each raw `saveScreenshot` is `2400x1600` (still 3:2). `make screenshots` runs the spec, then **downscales every `screenshots/*.png` to exactly `1200x800` via `sips -z 800 1200`** (height-then-width; both source and target are 3:2, so no distortion). The downscale lives in the Makefile, NOT the spec, because e2e specs may not import node builtins. `sips` is macOS-only - on other OSes the target prints a fallback (`mogrify -resize 1200x800`).
- **The five shots, in order:** (1) a note *about the plugin* with only `created`/`updated`/`viewed` in Properties plus a single-line feature list in the body; (2) bulk-populate `fill-missing` preview (blue Run, "N skipped" shows the safe default); (3) reformat preview with the ambiguous day/month guard (red Run); (4) the settings tab; (5) the gitignore-style filter rules (on their declarative sub-page - the spec navigates there via `settingsTab.openSubPage('Files and folders to skip')`). Each carries a two-line benefit caption banner, injected into the DOM as a `<style>`+`<div>` in the Maple Mono font; the window is `1200x800` (3:2 store ratio; the diff modals, capped at `min(85vw, 900px)`, sit centered) and the editor uses full width (`readableLineLength` off).
- **Electron/chromedriver gotchas** (all because Obsidian's chromedriver lacks the `Browser.getWindowForTarget` CDP command): the window is resized via Electron's own window API through the `require` Obsidian exposes to plugins (not `browser.setWindowSize`, which throws); a settings section is scrolled into view with an in-page `scrollIntoView` (wdio's Actions-API `scrollIntoView` otherwise hangs to the mocha timeout); and the banner/scroll helpers do all DOM work through `activeDocument`, never the global `document`. That is deliberate, NOT cosmetic: these helpers must not carry `eslint-disable obsidianmd/*`. The Obsidian review scanner ignores this repo's eslint config and wraps the recommended ruleset with a "this rule cannot be disabled" check, so an `eslint-disable obsidianmd/no-forbidden-elements`/`prefer-active-doc` that passes a naive `make lint` still FAILS review with `Disabling '<rule>' is not allowed` (a gating error). Using `activeDocument` both satisfies `obsidianmd/prefer-active-doc` (it is the recommended form) and sidesteps `obsidianmd/no-forbidden-elements` (which only matches `document.createElement('style'|'link')`, not `activeDocument.createElement(...)`); `styles.css` - the rule's intended fix - is inapplicable to a throwaway test banner, and inline styles would just trip `no-static-styles-assignment` instead. See "Replicate the scanner locally" below.
- **The banner is `prefer-create-el`-clean, and the way it got there is load-bearing.** Its `div`s use `createDiv()` (built directly in their final parent, since `createDiv` creates AND attaches). Its CSS is adopted as a **constructable stylesheet** (`new CSSStyleSheet()` + `replaceSync` + `activeDocument.adoptedStyleSheets`, removed again in `captionOff`) rather than injected as a `<style>` element - so no element is created and neither `prefer-create-el` nor `no-forbidden-elements` has anything to match. Do NOT "simplify" this back to `createElement('style')` (a `prefer-create-el` warning) and especially not to the rule's own suggested `activeWindow.createEl('style')`, which **escalates the warning into the blocking `obsidianmd/no-forbidden-elements` error** plus four `no-unsafe-*` errors - measured, not assumed. Construct the sheet with the bare global `CSSStyleSheet`, not `activeWindow.CSSStyleSheet` (untyped -> `no-unsafe-*` errors). `styles.css`, the rule's intended fix, stays inapplicable: these are capture-only styles and must not ship in the plugin's CSS.
- **`make test-e2e` overwrites these PNGs at raw 2x (2400x1600).** The marketing spec sits in the default `specs/**/*.e2e.ts` glob, so a full e2e run re-captures the five shots but does NOT run the Makefile's `sips` downscale - leaving them at double the store-required size. After any `make test-e2e`, either `git checkout -- screenshots/` (when no captured surface changed) or re-run `make screenshots` to regenerate them properly at 1200x800. Check `git status` before committing.
- **Keep them current (process rule):** after shipping any feature that changes a captured surface - the settings layout, a bulk modal, the note / Properties / editor view, or the filter-rules UI - re-run `make screenshots` and commit the refreshed PNGs. A stale screenshot is a silent regression in the store listing.

## Architecture

- **`src/main.ts`** - `FrontmatterDateManagerPlugin` (extends `Plugin`). Entry point. Handles vault events (`modify`, `create`, `rename`, `delete`) plus the workspace `file-open` event via `handleFileOpen()`, which stamps the `viewed`/last-viewed key when that feature is enabled. Per-file debouncing (2s). SHA-256 content hashing to detect real changes. Optionally maintains an opt-in edit-activity counter (`countUpdatesEnabled`, off by default) that increments `updated_count` by one on each real edit, in the same `processFrontMatter` call as `updated` (see Edit-activity counter in Key Patterns). Hash cache persisted to `hash-cache.json` with LRU eviction, debounced flushing, GC on startup, auto-population, and pruning of invalid/old-format cache entries on load. Pause/resume with countdown timer and status bar indicator (clicking the status bar toggles auto-update). `onExternalSettingsChange()` reloads settings when `data.json` is changed externally (e.g. by sync); both `onload` and this path run the loaded `data.json` through `sanitizeSettings()`, so a wrong-typed field can't crash startup (see Key Patterns); it also calls `settingsTab.update()` (the tab instance is kept on the plugin) because the declarative settings tree is a snapshot that would otherwise go stale - the e2e `setSettings` helper mirrors this. Three commands: `update-timestamps-current-file` (its ignored/blocked results map to per-cause notices via the exhaustive pure `ignoreReasonToNotice()`), `toggle-auto-update`, `pause-auto-update`. `shouldFileBeIgnored()` returns a discriminated `{ ignored: true; reason: IgnoreReason } | { ignored: false; fileContent }` (`no-path` | `not-markdown` | `canvas` | `excalidraw` | `filter-rule` | `empty` | `unchanged`), widened in `FileChangeResult` with `not-a-file` / `no-date-keys` / `invalid-file-times`; `getWriteBlock()` is the single write-safety gate ('markdown' | 'excalidraw' | null) shared with bulk (see Excalidraw drawings in Key Patterns). Uses `processingFiles` Set to prevent concurrent modifications of the same file. `log()` and `logError()` are public methods gated behind `__DEV_MODE__` - used by modals and other files for dev-only logging.
- **`src/filterRules.ts`** - Gitignore-style filter rule engine. Pure functions, no Obsidian dependency. `parseFilterRules(text)` parses multiline text into `FilterRule[]` with validation errors; it accepts `unknown` and returns no rules for a non-string input (defense-in-depth against a corrupt `data.json`, see Key Patterns). `isFileExcluded(filePath, rules)` applies rules top-to-bottom (last match wins).
- **`src/Settings.ts`** - `FrontmatterDateManagerSettings` interface + `FrontmatterDateManagerSettingsTab` (settings UI). `HashTrackingMode` type (`'body'` | `'frontmatter'` | `'both'`). The tab is **declarative** (Obsidian 1.13 `getSettingDefinitions()`; there is NO `display()` override): it returns a plain-data tree that Obsidian renders, indexes for global settings search, and auto-binds to `plugin.settings` keys. Tree order: an intro render row, the unheaded **dates** group (enable toggle + property name for `created`, `updated`, the opt-in `updated_count` counter, and `viewed` - conditionality via `visible` predicates), an all-dates-off hint row, then **Date formatting**, **Behavior** (auto-update, min-seconds slider, the **Filter rules sub-page** `type:'page'` with the textarea editor / preview / syntax reference as render rows (all three deliberately **unnamed** - the sub-page header already prints the title, and naming the editor row printed it twice on one screen) and a live `displayValue` rule count, hash toggle + mode dropdown + exclude input), the top-level native exclude **list** (`type:'list'`, `onDelete`; a list cannot nest inside a group, so it carries its OWN `heading` - without one the rows render as an unlabeled card wedged between two sections, with no visible tie to the input row above), **Modified-before-created dates**, the **Advanced sub-page** (new-file delay, cache auto-populate + max size as `number` controls, and the post-update command dropdown as a **render row** - a `control` dropdown would freeze the command list inside the load-time definitions snapshot, hiding commands from later-loading plugins for the whole session; the render row re-enumerates `app.commands` on every render), and **Bulk operations** (five `render` rows with buttons - `action` rows cannot carry the stable e2e classes). Every group/page after the hint carries `visible: () => !allDatesOff()` - the replacement for the old `display()` early return. Cross-cutting invariants: `getSettingDefinitions()` runs on every `update()` AND once at `addSettingTab()` registration (search indexing), so it must stay cheap and DOM-free - all DOM work lives in `render` callbacks (this also keeps the tree unit-testable, `settingsTabDefinitions.test.ts`); every `render` callback that creates elements on `setting.settingEl` MUST return a cleanup detaching them - the framework's in-place re-render (`update()` while the tab is open) only clears `controlEl`, so un-cleaned `settingEl` children duplicate on every `update()` (verified against the 1.13.4 runtime); any block a render row appends to `settingEl` needs an explicit **`width: 100%`** in `styles.css` - `.setting-item` is a flex row, so a bare block shrinks to its content and gets pushed right by the row's empty `.setting-item-info` (bit the intro, the all-dates-off hint, and the filter syntax reference; the `-timezone-error` div is deliberately exempt - it belongs under the input on the right); the definitions are a **snapshot** - after mutating data that feeds the tree (exclude keys, external settings change) call `this.update()`, never `display()`; the overridden `setControlValue(key, value)` is the single write funnel (trims the four `header*` property-name keys, persists via `plugin.saveSettings()`, and dispatches per-key side effects: `filterRules` -> `recompileFilterRules()`, `enableAutoUpdate` -> `updateStatusBar()`, `hashTrackingMode` -> rebuild-cache `Notice`) - render rows that save a single key route through it too, as do the exclude-list add/remove writes (`frontmatterHashExcludeKeys`); `getControlValue` is NOT overridden (the default reads `plugin.settings[key]`). `validate` callbacks are a **UI gate only** (empty property names, counter-vs-date-key collision both directions while the counter is enabled, inline errors on the number controls via `min: 0`) - `sanitizeSettings` remains the storage boundary. Rows a control cannot express stay `render`: date format (live preview desc rebuilt per keystroke), timezone (`TimezoneSuggest` needs the raw `inputEl`; invalid IANA input shows an inline `-timezone-error` div and never saves), the filter-rules editor (bad lines must still save + per-keystroke feedback, which `validate` cannot express), the exclude comma-input. Also exports the pure `sanitizeSettings(raw)` boundary validator (no Obsidian dependency, unit-tested) that coerces every wrong-typed field from an external `data.json` back to its `DEFAULT_SETTINGS` default while preserving unknown keys; it also resets a blank/wrong-typed `headerUpdateCount` and DISABLES the counter when its name collides with an enabled date key (see Key Patterns).
- **`src/bulk/`** - Shared building blocks composed by all five bulk modals (there is no longer a `BaseBulkModal`). `write.ts` (`applyFrontmatterWrite(app, plugin, file, mutator)` - the one safe frontmatter mutation: `processFrontMatter` without `{ctime,mtime}`, then `lastPluginWriteMtime` + hash-cache refresh), `scan.ts` (`runBatchedScan` - batched per-file compute with progress + abort, yields every `SCAN_BATCH_SIZE`=50 files), `executePhase.ts` (`runExecutePhase` - execute loop that owns `bulkRunning`, counts per-file errors without aborting, **collects each failure as `{label, message}` in `result.failures`** so the modal can show the user which files failed and why - `logError` is a no-op in production, so the console cannot carry these details; supports abort + `onComplete`), `chrome.ts` (shared render helpers `renderHeader`/`renderButtonBar`/`renderWarning`/`renderSummary`/`renderPaginatedDiffTable`/`renderDownloadPreviewButton`/`renderFailureTable`/`renderProgress` + `PREVIEW_MAX_ROWS`=100, now the table page size; `renderFailureTable` renders `result.failures` as a paginated `File | Error` table + Download), `pagination.ts` (pure `getPageCount`/`clampPage`/`getPageSlice` page math - unit-tested), `export.ts` (pure `toTSV` + `downloadPreviewAsFile` - the full diff downloaded as a local TSV file via a transient object-URL anchor; no clipboard, no vault file; **desktop only** - the download button is hidden on mobile via `Platform.isMobileApp` in `renderDownloadPreviewButton` because the `download` attribute can no-op silently in Capacitor; no clipboard fallback, which would re-add the disclosure), and `PhaseModal.ts` (thin `Modal` subclass: phase navigation `goTo`/`back`/`isOpenState` only - no operation logic). `renderPaginatedDiffTable` shows the FULL diff a page at a time (Prev / "Page X of Y" / Next, pager hidden at ≤1 page; only the current page's tbody lives in the DOM), so no row cap hides changes; it re-renders only the tbody + pager on page change. DOM rendering in `chrome.ts`/`PhaseModal` is not unit-tested (the `obsidian` mock no-ops DOM); the testable seams are `write.ts`, `scan.ts`, `executePhase.ts`, `pagination.ts`, `export.ts`, and each modal's `compute*`/`rebuildAll` methods.
- **`src/UpdateAllCacheData.ts`** - Modal (extends `PhaseModal`) for rebuilding the SHA-256 hash cache for all files. Non-destructive: a confirm screen (file count, blue Run, disabled at 0 files) → execute. Uses `populateCacheForFileDirect` per file and an `onComplete` that evicts + marks dirty + flushes; the rebuild core is the testable `rebuildAll()` method.
- **`src/BulkPopulateTimestampsModal.ts`** - Wizard modal for bulk-populating frontmatter timestamps from filesystem dates (`ctime`/`mtime`). Three-phase flow: configure (mode/override selection + platform warnings) → preview (dry-run with paginated full-diff table + download full preview) → execute (progress bar). Supports `PopulateMode` (`'created'`|`'updated'`|`'both'`) and `OverrideMode` (`'fill-missing'`|`'overwrite-all'`). Uses `Platform.*` API for platform-specific ctime reliability warnings. Extends `PhaseModal` and composes the `src/bulk/` blocks.
- **`src/RenameKeyModal.ts`** - Wizard modal for renaming frontmatter keys across all files. Three-phase flow: configure (old/new key names + delete toggle) → preview (paginated full-diff table with conflict detection + download full preview) → execute (processFrontMatter rename + optional delete). Scans ALL markdown files (`vault.getMarkdownFiles()`), not just filter-eligible ones. Extends `PhaseModal` and composes the `src/bulk/` blocks.
- **`src/inversionDetection.ts`** - Pure functions for detecting `updated < created` inversions and computing fixes. `isInversion(created, updated, toleranceSec)` is symmetric and tolerance-aware; `applyInversionFix(strategy, sources)` returns new Date objects per the strategy (`created-to-updated`, `updated-to-created`, `max-all`). No Obsidian dependency.
- **`src/FindInversionsModal.ts`** - Bulk modal (extends `PhaseModal`). Detection-first and dual-purpose (report + fixer): opens straight into a preview that auto-scans via `runBatchedScan` (per-file `computeInvertedForFile` runs inside the batch so large vaults don't freeze), then shows the paginated full inversion table (`renderPaginatedDiffTable`, Δ column accent via `columnClasses`) + download full preview + an inline strategy dropdown + tolerance hint, with a red `Run` disabled until a non-`disabled` strategy is chosen (no Configure phase, no Back). Changing the strategy refreshes only the warning + Run button, never the table, so the current page is preserved. `computeInvertedFiles` delegates to `computeInvertedForFile` (both covered by tests). `processFile` applies the selected strategy and writes via `applyFrontmatterWrite`.
- **`src/ReformatDateModal.ts`** - Wizard modal for standardizing date formats across all files. Three-phase flow: configure (target format display + scope dropdown) → preview (auto-detect existing formats, show conversions in a paginated full-diff table + download full preview) → execute (processFrontMatter rewrite). Has public `tryParseDate()`, a thin delegate to the pure `parseDateValueWithZone` helper (`src/utils.ts`) that auto-detects formats via `parseISO`, common date-fns format strings, and a native `Date()` fallback - all anchored to the configured timezone so parse is the inverse of `formatDate` (see Key Patterns). ### Key Patterns

**File modification pipeline** (spans `main.ts`):
vault `modify` event → per-file debounce (2s) → `processFileWithLock()` → ignore checks (gitignore-style filter rules via `isFileExcluded()`) → read file → `getContentForHashing()` (body/frontmatter/both per `hashTrackingMode`) → SHA-256 hash → compare with cache → if changed: `computeFrontmatterUpdates()` → `processFrontMatter()` → re-hash updated file → mark cache dirty → debounced cache flush to disk. When `minSecondsBetweenSaves` blocks an otherwise-needed update, `computeFrontmatterUpdates()` returns `retryAfterMs`, the hash is deliberately NOT cached, and a retry is scheduled so the still-pending change is re-detected. **`retryAfterMs` takes precedence over writing in the same pass:** `handleFileChange` checks it BEFORE `hasChanges`, so when `updated` is rate-limited it defers the WHOLE update - including a missing-`created` fill - to the retry, rather than writing `created` now and silently dropping the retry. Writing in that pass would refresh the hash (absorbing the body change) and permanently lose the still-pending `updated` bump; deferring keeps the proven no-write retry path (no `processFrontMatter` → no self-trigger token → no hash refresh). The `created` fill is non-urgent (sourced from immutable `ctime`), so the short defer is safe. Covered by `handleFileChange.test.ts` (direct unit tests for this entry point and its self-trigger / malformed-YAML / rate-limit-retry guards).

**Freshness / no-op-write guard** (`main.ts` `computeFrontmatterUpdates` `updated` branch + `handleFileOpen` `viewed` write, `FRESHNESS_SEC` in `constants.ts`):
The automatic `updated` write and the `viewed` write are skipped when re-stamping would be a near-no-op - the fix for the delayed redundant write that "shook" notes an external script had already stamped. Two-part guard, both checks run in `computeFrontmatterUpdates` for `updated` (mirrored raw-only for `viewed`): **(a) raw value-identity** - if `String(candidate) === String(existingUpdated)` the value FDM would write already equals the on-disk value, so it is a no-op; compared **raw, BEFORE `parseDate`, on purpose** so all-digit non-epoch formats (e.g. `yyyyMMdd`) that `parseDate` would misread as an epoch are still covered. **(b) asymmetric/signed freshness** - if `(mtime - parseDate(updated)) / 1000 <= FRESHNESS_SEC` (= 5), `updated` already covers mtime or is ahead of it, so the existing value is preserved; signed so a deliberately **future-dated** value is never clobbered and sub-window drift (a script that stamped a second or two before mtime) is absorbed - an accepted **≤5 s precision loss**, well inside the plugin's tolerance. **Invariant:** FDM never writes `updated`/`viewed` unless the value would actually change (raw-different) AND `updated` is genuinely stale (> `FRESHNESS_SEC` behind mtime, or unparseable). On a guard skip, `computeFrontmatterUpdates` omits `updatedValue`/`retryAfterMs`/`countedEdit`, so `handleFileChange` takes its existing "no changes" branch: it just refreshes the hash cache and stops - the pending change resolves on the FIRST pass, with **no retry and no counter increment** (a genuine edit within the window is coalesced into the guard - the documented precision tradeoff). The still-parseable-but-stale and rate-limited paths are unchanged (they still write / defer). `handleFileChange`'s ok result is `{ status: 'ok'; wrote: boolean; deferred?: boolean }`; `wrote` is `true` only when `processFrontMatter` actually ran, and `deferred` is `true` only on the rate-limited retry path (a real change IS pending, to be written on the retry). So the manual "Update timestamps for current file" command reports "Timestamps updated." only on a real write, "Timestamps will update shortly." (`notices.timestampsUpdateScheduled`) when the write is merely deferred, and "Timestamps are already up to date." on a guarded skip - never a false "updated" and never a false "already up to date" when a write is imminent. **Two limits (not bugs):** Obsidian may still reload an open note on the external write itself (outside FDM's control); and a cold hash cache can still make the first sync-induced `modify` look like a real edit (mitigated by hash-cache auto-populate). Covered by `handleFileChange.test.ts` / `handleFileOpen.test.ts` (identity / drift / future / absorb / genuinely-stale / midnight-boundary) and the manual e2e `external-fresh-updated.e2e.ts` (F1 external fresh `updated` → no re-stamp with a `modify`-fired proof + mtime-unchanged settle; F2 control body-only edit → one re-stamp).

**Self-triggered modify event detection** (`main.ts`):
Self-triggered modify events (`processFrontMatter` fires `modify` after writing) are detected via the `lastPluginWriteMtime` Map: store `file.stat.mtime` immediately after the write, then check it in `handleFileChange` before processing. This guard is independent of whether mtime was preserved on the write - it stores whatever `file.stat.mtime` is post-write and the self-triggered event carries that same value, so it matches and is skipped either way. This applies to ALL automated `processFrontMatter` calls (`handleFileChange`, `handleFileOpen`) and every bulk write.

**Dirty-editor-buffer write guard - never write into a live buffer with unsaved changes** (`main.ts` `markdownViewsFor` / `hasUnsavedEditorChanges`; issue #10). This is the plugin's editor-safety mechanism. It replaced an earlier `{ ctime, mtime }` pin (`editorSafeWriteOptions`, removed in the fix) whose rationale was verified FALSE against Obsidian's own code (`obsidian-1.12.7.asar`, `obsidian-1.13.6.asar`) and by `e2e/specs/editor-dirty-merge.e2e.ts` on real Obsidian. **Never reintroduce an mtime pin, and never restate the old "pinning mtime stops the reload" explanation.** What Obsidian actually does:

- `TextFileView` keeps a private `dirty` flag (set by `requestSave()`, cleared by `save()`, whose debounce is 2000 ms and **non-resetting**, so a continuously typing user flushes to disk roughly every 2 s). On every vault `modify` of its own file it re-reads the file and, **iff `dirty` is true** (plus base/buffer/disk all differing), runs a FUZZY diff-match-patch 3-way merge - discarding `patch_apply`'s per-hunk success flags - and shows `"<file>" has been modified externally, merging changes automatically.` **mtime is never consulted on this path**, so pinning it could not prevent the reload, the merge, or that notice.
- The adapter emits `modified` when **mtime OR size** changed. Adding a property grows the file, so the event fired despite the pin. Conversely, when a re-stamp changed the value but **not** the byte length (the norm for a fixed-width `dateFormat` such as the default `yyyy-MM-dd'T'HH:mm:ss`) and mtime was pinned, **no event was emitted at all**: the open editor never learned about the write and its next save silently reverted the plugin's stamp (e2e D9). Removing the pin also disambiguates the `lastPluginWriteMtime` self-write token.

**The guard.** `hasUnsavedEditorChanges(file)` returns true when ANY Markdown leaf showing that file is not provably clean. It is now the Markdown half of `getWriteBlock(file)` ('markdown' | 'excalidraw' | null), the single gate every write path consults (the Excalidraw half is in the Excalidraw drawings pattern below): it reads the private `dirty` through an `unknown` cast (the established internal-API pattern, cf. `app.commands`), and **fails closed** - a non-boolean `dirty` (API drift) falls back to `view.getViewData() !== await vault.cachedRead(file)`, and an unreadable buffer counts as dirty. ALL matching leaves are checked, never the first: one leaf can be clean while another holds unsaved changes (e2e D4). Per write path:

- **`handleFileChange`** (automatic + the manual command): the guard runs after `shouldFileBeIgnored` and **before `computeFrontmatterUpdates`** (a compute for a pass that cannot write is wasted work). On a dirty buffer it defers the WHOLE pass in the exact shape of the rate-limit branch - no write, **no hash refresh** (refreshing would absorb the pending change and lose it), one coalesced per-file timer, `MODIFY_DEBOUNCE_MS` - and returns `{ status: 'ok', wrote: false, deferred: true }`, which the manual command already reports as "Timestamps will update shortly." **There is deliberately no deferral cap:** a cap would eventually force the unsafe write, and Obsidian's own 2 s autosave clears `dirty` shortly after typing stops, so deferral cannot starve.
- **`handleFileOpen`/`viewed`**: the stamp is **dropped, not deferred** - `viewed` means "at open", so a later write would record a false time.
- **Bulk** (`applyFrontmatterWrite`): throws the `BulkSkipped` sentinel, so the file is **skipped visibly** rather than deferred - a bulk run can be cancelled or its modal closed, and a later silent write would break the mandatory dry-run contract. See "Bulk skip on unsaved changes" below.
- **The manual command** routes through `processFileWithLock` (which now returns the result) so it can never race an in-flight automatic pass; a locked file maps to `deferred`. It deliberately does **not** force `view.save()`: with several leaves on one file, flushing one proves nothing about the others, and it would write the user's content unasked.

**Consequences accepted with the fix:** with last-viewed enabled, opening a note now moves its `mtime` (if that ever becomes unacceptable, the answer is to move `viewed` out of frontmatter, not to fake timestamps); and `updated` lags while the user is actively typing.

**Known residuals (documented, not built - reviewed by Codex + three independent skeptics, all judged not worth blocking on):**

- **TOCTOU:** `getWriteBlock` and `processFrontMatter` are separated by an await, so a keystroke landing in that few-ms gap still hits the merge branch. Cannot be closed without an atomic Obsidian API - the guard reduces the merge to near-zero, it does not eliminate it.
- **The deferral has no backoff, deliberately.** Each retry re-runs `shouldFileBeIgnored` FIRST, so every 2 s tick costs a `vault.read` + SHA-256 (the hash never matches - the deferral does not refresh it) plus the leaf scan. Judged acceptable: the loop is bounded by the note staying open, and it only becomes endless if BOTH the private `dirty` drifts to a non-boolean AND the public fallback persistently reports a clean buffer as differing from disk - and a clean buffer equals disk by construction, so the fallback's normal answer is "clean" (pinned by a unit test). Do NOT add a deferral cap that forces a write; if this ever needs attention the fix is a diagnostic tripwire, not backoff. **Revisit signal:** users reporting that the manual command keeps saying "Timestamps will update shortly" on a note they are not editing.
- **A pending deferral evaporates on rename:** the rename handler clears the old path's timer and never re-arms it under the new path, and rename fires no `modify`. The hash cache entry is migrated with its pre-edit hash, so the next real edit still converges - but that one `updated` bump is lost. Same class as the pre-existing rate-limit retry; belongs with the pending-write task below.
- Editable embeds (`![[note#heading]]`) hold their own dirty buffer for the same `TFile` and are invisible to `getLeavesOfType('markdown')` - do not build a private `_children` traversal until such a buffer is proven independently dirty; other writers (Sync, obsidian-git, Linter-on-save, Templater) trigger the identical notice.
- **Separate task (pre-existing, widened by this change):** a deferred edit can be absorbed when a bulk run or "Rebuild cache" refreshes that file's hash mid-deferral; and a pending retry can overlap a bulk write, because `bulkRunning` only gates new vault events and bulk writes do not take `processingFiles`. **That overlap cannot corrupt YAML** - verified in `obsidian-1.12.7.asar`: `processFrontMatter` -> `vault.process` -> `queue` (`this.promise.then(e,e)`) is one serial promise chain, so calls interleave as whole read-mutate-write units. The real symptom is a redundant or clobbered write. Fix direction: one per-file mutex across automatic/viewed/bulk, plus a content fingerprint instead of the `lastPluginWriteMtime` token. **NOT reproduced** in 11 e2e scenarios: keystroke loss, an altered in-progress wikilink, a closed suggester - the merge fires but CodeMirror's `set(data, false)` replaced only the frontmatter lines. Treat the data-loss branch as a proven MECHANISM with no observed occurrence.

Covered by `handleFileChange.test.ts` / `handleFileOpen.test.ts` / `bulk/write.test.ts` / `bulk/executePhase.test.ts`, and by the e2e `editor-dirty-merge.e2e.ts` (11 scenarios; 9 failed on 1.2.1, D8/D10 are controls) + `editor-safe-write.e2e.ts` (the clean-buffer happy path).

**Excalidraw drawings - tracked by default, never written to while the drawing is dirty** (`main.ts` `isExcalidrawFile` / `excalidrawWriteBlock` / `getWriteBlock`, `constants.ts` `EXCALIDRAW_*`, setting `trackExcalidraw`; issue #15). Drawings are ordinary `.md` notes carrying a truthy `excalidraw-plugin` frontmatter marker. They were skipped by a hardcoded undocumented rule inherited from the upstream plugin (2023 rationale: writes reset the zoom - no longer true, `reload()` calls `preventAutozoom()`); the manual command then reported the misleading shared "ignored by plugin settings" notice. Decisions taken:

- **Seamless by default:** `trackExcalidraw` defaults to `true`; the toggle ("Include Excalidraw drawings", Behavior group) is the one-click opt-out. A glob filter rule is NOT a substitute - the `.excalidraw.md` suffix is an Excalidraw setting, the frontmatter marker is not. Framed as a MINOR release (removed undocumented exclusion + new switch), with a top Highlights bullet.
- **Detection reads `metadataCache`, not the `ExcalidrawAutomate` global** - the same truthy-marker check Excalidraw's own `FileManager.isExcalidrawFile` does. Sync, unit-testable, independent of the other plugin's load order (previously a drawing in a vault without Excalidraw running was NOT skipped). The `.excalidraw` extension branch is unreachable here - the `extension !== 'md'` gate runs first. **Classification is three-valued** (`classifyExcalidraw`: `drawing` / `not-drawing` / `unknown`): a cache MISS is not "ordinary note". Right after startup the marker is invisible, and treating that as a note would let the `viewed` stamp - the one write aimed at an idle drawing - or a toggle-off write through. `unknown` is resolved from the file text (`isExcalidrawContent`, same truthy-marker rule on the raw frontmatter block) wherever the text is at hand: `shouldFileBeIgnored` re-checks AFTER reading the file (so an unindexed ORDINARY note is not wrongly skipped), and `handleFileOpen` passes the content it already got from that check. With no text available `isExcalidrawFile` fails closed (treats the file as a drawing) - the caller is about to skip a write, and a skipped write is recoverable.
- **`viewed` is never stamped on a drawing**, toggle-independent: the file-open write is the only FDM write that can land on a drawing idle > 5 min, and Excalidraw answers that with a full `reload(true)` (flash, scene re-parse, undo loss). `updated` never hits that path - it always follows a fresh Excalidraw save.
- **The guard (`excalidrawWriteBlock`) fails CLOSED and is modify-driven.** Idle and mounted must be PROVEN, never merely "not obviously broken": `view.file.path` must be a string (a view still mounting blocks every write - a millisecond-long window whose only cost is a delayed stamp), `semaphores.saving`/`autosaving` must both be exactly `false` (a partial-drift `{}` leaves them `undefined`, which is NOT idle), `excalidrawAPI` must be an object, and `isDirty()` must exist, not throw, and return exactly `false`. Verified in Excalidraw 2.26.4: `FileManager.modifyEventHandler` consumes `preventReload`, else - if `lastSaveTimestamp + 300000 < now` - runs `reload(true)` + `clearDirty()`, DISCARDING unsaved strokes; otherwise it only syncs scene elements. A drawing CAN stay dirty that long (autosave is skipped while a text element / new element / freedraw is active, and can be disabled). Writing into a CLEAN open drawing is safe: Obsidian core refreshes the view buffer (`TextFileView.onModify -> loadFileInternal -> setData`, verified in `obsidian-1.13.7.asar`; Excalidraw never sets core `dirty` - `requestSave` is nulled in `onClose`), so the header its next save re-serializes is the fresh one. The guard blocks when `isDirty()` is not exactly `false`, `semaphores.saving|autosaving` is true, or `semaphores`/`isDirty`/`excalidrawAPI` are missing/malformed (API drift, view not mounted) - these are public ExcalidrawView members but NOT a stable cross-plugin API, so every read goes through an `unknown` cast.
- **Dirty and busy are different blocks.** `getWriteBlock` returns `'excalidraw-busy'` while a save is in flight (`saving`/`autosaving`) - a short-lived state that DEFERS on the normal 2 s timer, because that save's own `modify` may already have been delivered and waiting for "the next one" could strand the update until the user edits again. Bulk skips both (it cannot wait, and writing mid-save would race Excalidraw's serialization).
- **A dirty-or-unknown block is DROPPED, not deferred** (`handleFileChange` returns `{ status: 'ok', wrote: false, blocked: 'excalidraw' }`): no write, **no hash refresh**, and deliberately **no retry timer** - the Markdown 2 s retry rationale ("Obsidian autosaves 2 s after typing stops") does not transfer, and polling a multi-MB drawing every 2 s for hours is pure waste. Excalidraw's own next `save()` fires `modify`, which re-triggers the pipeline. Bulk throws `BulkSkipped` with its own reason string (`skippedExcalidrawUnsaved`) so the skipped table tells the user to save the drawing.
- **Rename key / Reformat dates keep their "every Markdown note" contract** (explicit previewed maintenance ops, they already ignore filter rules) - with the default ON this is no longer an inconsistency. Documented in README and the toggle description.
- **Accepted residuals:** TOCTOU between the guard and `processFrontMatter` (needs an atomic API to close). Writing into a CLEAN but long-idle open drawing (no save for > 5 min) still makes Excalidraw reload it from disk - a visible re-render, but NOT data loss: the view equals disk by definition, and `reload -> loadDrawing` does not call `api.history.clear()` (verified in ExcalidrawView 2.26.4 - the only `history.clear()` call sites are `setTextMode` and two text-element edit paths), while `preventAutozoom()` keeps the zoom. Blocking that case was considered and rejected: it would make bulk operations permanently skip any open drawing. Also cosmetic: a toggle-off drawing inside a filter-excluded folder reports the Excalidraw reason (the Excalidraw check runs first), and a blank-date-keys config plus a dirty drawing reports "will update after Excalidraw saves it" (the block check precedes the no-date-keys check) - neither writes anything. **Separate follow-up task (not done here):** the manual command still passes the hash gate, so it cannot re-fill a hand-deleted `created` while the body is unchanged (it now says "No content change detected since the last update" instead of a false "already up to date").

Covered by `shouldFileBeIgnored.test.ts` / `handleFileChange.test.ts` / `handleFileOpen.test.ts` / `bulk/write.test.ts` and the manual e2e `excalidraw.e2e.ts`, which drives the REAL Excalidraw plugin.

**No write path preserves mtime** - neither the automatic single-file writes nor bulk pass a `{ ctime, mtime }` argument to `processFrontMatter`. Every bulk modal writes through the single canonical `applyFrontmatterWrite()` (`src/bulk/write.ts`), which also sets `lastPluginWriteMtime` and refreshes the hash cache via `populateCacheForFile`. Preserving mtime for bulk would additionally leave the hash cache stale and let a self-triggered modify event escaping the `bulkRunning` window spuriously re-stamp `updated` (`bulkRunning` alone is insufficient - those events arrive asynchronously, often after it resets to `false`).

**Bulk skip on unsaved changes** (`src/bulk/write.ts` `BulkSkipped`, `executePhase.ts` `ExecuteSkip`/`skipped`, `chrome.ts` `renderSkippedTable`):
`applyFrontmatterWrite` throws the exported `BulkSkipped` sentinel instead of writing when `getWriteBlock(file)` is non-null - with a distinct message per cause (`skippedUnsavedChanges` for a dirty Markdown buffer, `skippedExcalidrawUnsaved` for a dirty/busy Excalidraw view). `runExecutePhase` catches it SEPARATELY from real errors: it does not increment `errors` and does not land in `failures`, but collects `{ label, reason }` into a new `skipped[]` field on `ExecutePhaseResult`. All four mutating modals render it after the done-header via `renderSkippedTable` (paginated `File | Reason` + Download, its own `frontmatter-date-manager-bulk-skipped*` classes and the warning accent - a skip is NOT a failure). The skipped file is deliberately NOT requeued or retried in the background: the preview is a historical snapshot, and a later silent write would break the mandatory dry-run contract - the reason string tells the user to save/close the note and run a new preview.

**Inversion prevention** (`main.ts` in `computeFrontmatterUpdates` + `handleFileChange`):
After computing candidate `createdValue`/`updatedValue`, check the final pair (falling back to existing frontmatter values). If `isInversion()` returns true under the configured tolerance, apply `applyInversionFix()` with the configured strategy and set `inversionFixed: true` on the result. `computeFrontmatterUpdates` is PURE - it must never notify: `handleFileChange` calls `showInversionNoticeOnce()` (one-time-per-session) only AFTER a `processFrontMatter` call that actually succeeded, so a deferred (dirty buffer, rate limit) or failed pass can never announce a fix that did not happen. Default strategy is `disabled` - the prevention block is no-op for existing users until they opt in.

**Edit-activity counter** (`main.ts` `computeFrontmatterUpdates` + `handleFileChange`, `utils.ts` `coerceCount`, `Settings.ts` `sanitizeSettings`):
Opt-in (`countUpdatesEnabled`, default off; `headerUpdateCount` default `updated_count`). `computeFrontmatterUpdates` sets `countedEdit: true` ONLY when the modified-time branch writes a fresh `updated` for a real edit (no prior value / unparseable prior / `shouldUpdateValue` passed) - never on a created-only fill, a rate-limited defer (the increment rides the retry's real write, not the deferral pass), or the inversion-fix service rewrite of `updated`. In the `processFrontMatter` callback the counter increments iff `countedEdit === true && updatedValue !== undefined`, reading its base from THIS callback's `frontmatter` (the authoritative on-disk value, so a sync-merged count is respected) via `coerceCount(base) + 1` - a native number, so YAML stays unquoted. The count is therefore "edits that moved `updated`": the 2s debounce + `minSecondsBetweenSaves` coalesce a burst into ONE increment - an approximate activity signal, not an exact edit/keystroke count. The manual `update-timestamps-current-file` command DOES count (it routes through `handleFileChange`); bulk operations and `handleFileOpen`/`viewed` never count (they write via `applyFrontmatterWrite` / their own callback, not the counter path).
**Name-collision guard (double-defended, symmetric):** the counter and a date key must never share a key, or one `processFrontMatter` write would clobber the other. BOTH guards check ALL three date-key names (`headerCreated`/`headerUpdated`/`headerLastViewed`) UNCONDITIONALLY - not just the enabled ones: `sanitizeSettings` DISABLES the counter (never renames - a rename could re-collide) on any collision, and `counterKeyOrNull()` re-checks at the write boundary and returns `null` on any collision. Checking all three unconditionally (rather than only the enabled date keys) keeps the two guards symmetric - so the settings state always matches the write boundary (no silently inert "enabled but never writes" counter) - and covers the cases where a "disabled" date key still gets written: the inversion fix can stamp `created`/`updated` even when their toggle is off, and last-viewed can be re-enabled later.
**Hash exclusion (toggle-neutral):** `getContentForHashing` excludes the counter's configured key from the tracked hash UNCONDITIONALLY (regardless of `countUpdatesEnabled`), for two reasons: (1) the counter's own write must never re-dirty the hash, or it would drive a self-amplifying increment loop under `frontmatter`/`both` mode; (2) excluding a plugin-owned key always (not only when enabled) keeps the hashed content identical across a counter on/off toggle, so toggling never causes a spurious `updated` re-stamp on already-counted notes. Default `body` mode never hashes frontmatter, so it is unaffected either way.
Covered by `coerceCount.test.ts`, `handleFileChange.test.ts` (counter AC/R matrix), `sanitizeSettings.test.ts`, `getContentForHashing.test.ts`, and the manual e2e `update-count.e2e.ts`.

**Numeric epoch units - seconds vs. milliseconds** (`utils.ts` `epochNumberToDate`):
Epoch numbers arrive in two units - `file.stat.*` and `T`-format are ms, `t`-format is seconds - but `new Date(n)` assumes ms, so raw seconds (~1.7e9) resolve to ~1970 and corrupt `t`-format vaults. Always parse via `epochNumberToDate()` (disambiguates by magnitude, `< 1e11` → seconds), never bare `new Date(n)`. Used by `parseDate` and `parseDateValueWithZone` (which backs `ReformatDateModal.tryParseDate`).

**Timezone-anchored date parsing - parse must be the inverse of `formatDate`** (`utils.ts` `parseDateValueWithZone`):
`formatDate` always renders with `{ in: tz(settings.timezone) }` when a timezone is set, so any code that parses a stored date string back into a `Date` must parse in that SAME zone - otherwise a naive wall-clock value silently shifts by the host<->settings offset on round-trip, and a value already in the target format gets needlessly rewritten (the bug that motivated this helper: a blind `parseISO(str)` resolved against the host zone while `formatDate` used the configured zone). `ReformatDateModal.tryParseDate` delegates to the pure `parseDateValueWithZone(value, timezone)`, which builds `tzOptions` once and threads it through BOTH deterministic strategies (`parseISO(str, tzOptions)` and the `COMMON_DATE_FORMATS` loop) so no branch can drift to the host zone. An explicit offset in the string still wins (the `in` option only supplies a zone for offset-less values); the last-resort bare `new Date(str)` is deliberately left timezone-blind because re-anchoring an ambiguous locale/RFC string would discard an explicit zone (e.g. a trailing `GMT`) - a guess-and-overwrite. Empty timezone → `{}` → host zone, identical to formatting with no timezone, so the default config round-trips unchanged. Tests run under the host zone (vitest sets no `TZ`), so any timezone-regression test must pin the host zone (`vi.stubEnv('TZ', 'UTC')`) and configure a different `settings.timezone`, then assert against the configured-zone output - which is host-independent.

**File filtering** (`filterRules.ts` + `utils.ts`):
Single `filterRules` textarea with gitignore-style syntax. Lines are exclude patterns by default; `!` prefix re-includes; `#` for comments; last matching rule wins. Empty rules = all .md files tracked. `parseFilterRules()` parses text into `FilterRule[]` with error collection. `isFileExcluded()` evaluates rules top-to-bottom using `matchesPathPattern()` (picomatch for globs, prefix match for plain folder names). Compiled rules are cached in `_compiledRules` on the plugin instance and recompiled on settings change.

**Bulk operations and hash bypass** (`src/bulk/`, `main.ts`):
Bulk operations (populate from filesystem, rebuild cache, find inversions) skip the content hash check in `shouldFileBeIgnored()` by passing `{ skipHashCheck: true }` to `getAllFilesPossiblyAffected()` at the file-listing stage. The hash check exists only for automatic change detection on `modify` events - it must not filter files during intentional bulk processing. Per-file, the bulk modals write through `applyFrontmatterWrite` (never through `handleFileChange`), which sets `lastPluginWriteMtime` and refreshes the hash cache.

**Destructive operation UX**:
Every bulk operation that mutates note data must present a **mandatory dry-run preview** before any write - the user cannot reach Run without first seeing the exact diff. This preview is the primary safeguard, and it must show **every** changed row, not a truncated sample: the four diff modals render through `renderPaginatedDiffTable` (`src/bulk/chrome.ts`), which paginates the full in-memory diff (`PREVIEW_MAX_ROWS`=100 per page, Prev/Next pager) so large vaults stay responsive without hiding rows. Each also offers a neutral **Download full preview** button (`renderDownloadPreviewButton` → `downloadPreviewAsFile`, `src/bulk/export.ts`) that downloads the complete diff as a local TSV file via a transient object-URL anchor - no clipboard access, no vault file is written - placed between the table and the action bar. The clipboard was deliberately dropped (it was the plugin's only `navigator.clipboard` use) to remove the "Clipboard Access" capability disclosure from the Obsidian community scorecard; see Capability disclosures below. The three wizard modals (populate, rename, reformat) use a configure → preview → execute flow; find-inversions is detection-first (auto-scan on open, inline strategy, table on the same screen as Run); rebuild-cache is a non-destructive confirm screen. The unifying invariant: red iff the operation replaces or deletes existing user values; blue iff it only adds missing values or touches sidecar data. Destructive cases - overwrite-all populate, fix inversions, rename with delete/overwrite, and reformat (which always rewrites existing date strings in place, so its Run is unconditionally red) - must be red and restate the consequence at the point of action ("cannot be undone" / "irreversible"). Non-destructive modes (fill-missing populate, pure-copy rename, rebuild cache) stay blue. The Run button is rendered via `renderButtonBar({ primary: { destructive } })` (`src/bulk/chrome.ts`): the primary is always `.setCta()`, and `destructive: true` additionally applies `.setDestructive()` (the documented 1.13 composition for a destructive primary action; toggling off uses `.removeDestructive()`); each modal sets the flag from its selected mode (or unconditionally for the always-destructive operations). Bulk buttons are placed last in the settings section. Use `.setDestructive()` for the red style - `.setWarning()` is deprecated since 1.13 and must not come back. When an execute phase finishes with per-file errors, the modal must surface **which** files failed and **why** in-place via `renderFailureTable` (a paginated `File | Error` table + Download) - never tell the user to "check the console", which is empty in production because `logError` is gated behind `__DEV_MODE__`. The same applies to files the run deliberately skipped (unsaved editor changes): `renderSkippedTable`, rendered separately from failures - see Bulk skip on unsaved changes. The single-file "Update timestamps for current file" command follows the same rule: it shows the real reason from `result.error` (via `errorToMessage`) in a `Notice`, not a console pointer.

**Hash cache lifecycle** (`main.ts`):
Stored in `hash-cache.json` as `Record<string, {hash, lastAccessed}>`. Loaded on startup with GC (removes entries for deleted files) and optional auto-population. Flushed to disk via debounced writes (30s debounce, 300s max delay). LRU eviction when exceeding configurable max size.

**Settings ingestion boundary - validate external `data.json` types** (`Settings.ts` `sanitizeSettings`, `main.ts` `loadSettings`):
`data.json` is external input (hand-editable, rewritten by sync/backup), exactly like `hash-cache.json` - so `loadSettings` runs the loaded object through the pure `sanitizeSettings(raw)` before use, mirroring the runtime type-validation `loadHashCache` already does. Every known field whose runtime type doesn't match its `DEFAULT_SETTINGS` default is reset to that default - including non-finite numbers, a non-array `frontmatterHashExcludeKeys` (a plain `typeof` check is insufficient: `[]` and `{}` are both `'object'`, so arrays are validated with `Array.isArray` + per-element string filter), and out-of-set `hashTrackingMode`/`inversionFixStrategy` enums (a wrong-value string passes `typeof`, so membership is checked explicitly). Unknown keys are preserved for forward-compat. This single boundary fix covers a whole class of "corrupt settings crash" bugs where a wrong-typed field flowed into code that asserts a type: `filterRules` → `parseFilterRules().trim()` killed `onload` with no UI recovery; `headerCreated/Updated/LastViewed` → `.trim()`; `frontmatterHashExcludeKeys` → `for...of`; `dateFormat/timezone` → date-fns. Validate once at the boundary, not per consumer. `parseFilterRules` additionally hardens its own input (accepts `unknown`, no rules for non-strings) as a second line of defense.

**Obsidian internal API access pattern**:
When accessing Obsidian APIs without public typings (e.g. `app.commands.executeCommandById`, `app.commands.commands`), use `unknown` intermediate cast - never `any`. Pattern: `const internalApp = this.app as unknown as { commands: { ... } };`. This satisfies both TypeScript and `@typescript-eslint/no-explicit-any`.

**`processFrontMatter` callback typing**:
The `frontmatter` parameter from `processFrontMatter()` is typed as `any` in Obsidian's API. Always annotate the callback parameter explicitly: `(frontmatter: Record<string, unknown>) => { ... }`. Similarly, `getFileCache()?.frontmatter` (typed as `FrontMatterCache` extending `Record<string, any>`) should be cast to `Record<string, unknown>` before accessing keys.

**Internationalization (i18n)** (`src/i18n/`):
The UI ships in 21 languages and follows Obsidian's app language automatically (no plugin setting). `index.ts` resolves the active locale **once at module load** from `getLanguage()` (`@since 1.8.7`; safe at the `1.11.0` floor, no `typeof`/`localStorage` guard): if the reported code is in `LANGUAGE_MAP` use it, else `'en'`. The settings tab re-renders on open, modals are constructed fresh, notices/status-bar read at call time - all read the already-resolved `strings`, so no reactive re-render is needed (changing Obsidian's language requires an app reload). `LANGUAGE_MAP` uses exact-match + explicit aliases mirroring notebook-navigator (`zh`/`zh-CN`/`zh_cn` -> Simplified, `zh-TW`/`zh_tw` -> Traditional, `pt-BR` -> Brazilian); do not "normalize" codes - dropping the `zh_cn`/`zh_tw` underscore forms would silently fall an underscore-form Chinese locale back to English. **`strings` is read-only:** `mergeTranslationValues` returns untouched subtrees **by reference** from `STRINGS_EN` (shared with the merged result), so never assign to `strings.*` at runtime - it would mutate the English source and every cached locale. **Static** strings are plain object properties; **dynamic** strings are `{token}` templates resolved by the pure `format()` (token name copied verbatim; unknown/missing tokens render the literal `{key}`, loud not silent). **No interpolation of translatable fragments** (a toggled state is two complete strings, never `'Auto-update {state}'`) and **no ICU plurals** (plain `{count}` substitution - accepted YAGNI tradeoff). `STRINGS_EN` is the type source-of-truth - **never `as const`** (leaves must infer as `string` so each locale's `Strings` values stay assignable). Locales are typed `Strings` (not `DeepPartial`), so a missing key is a compile error. Every locale declares every key; a value identical to English is allowed (the requirement is presence, not difference). The per-key English fallback in `index.ts` is kept as runtime defense-in-depth only. Two **value-integrity guards** in `i18n.test.ts` cover the defects per-key fallback does NOT save (a present-but-bad override wins the merge): no empty-string leaf where English is non-empty (would ship a blank label), and every translated leaf keeps English's exact `{token}` set (a mistranslated token would print the literal). A `locale completeness` test asserts every English key is present in every locale (a forgotten key fails the suite), and a coverage test asserts every locale's keys are a **subset** of English (catches typos/stale keys). Both are now also guaranteed by the `Strings` type. Sentence-case on extracted strings is no longer lint-checked (the rule inspects string literals, not `strings.*` references) - review it by hand in the single `en.ts`. **Out of scope (kept English):** `manifest.json` name/description (Obsidian cannot translate the manifest at runtime), note content/frontmatter values (safety invariant), the marketing-screenshots pipeline (runs in English), and `src/filterRules.ts` parse-error messages (`Empty pattern`, `Empty pattern after "!"`, `Invalid glob pattern`) - `filterRules.ts` is a pure Obsidian-free module (importing `strings` would pull in `getLanguage`) and one branch surfaces uncontrollable picomatch text; the error *wrapper* (`filterRules.parseError`) IS translated. Covered by `format.test.ts` and `i18n.test.ts`.

### UI & CSS conventions

Most of these are enforced automatically by `eslint-plugin-obsidianmd` plus the project rules in `eslint.config.mts` and `tsconfig.json` - run `make lint` and let it catch violations instead of memorizing the full list. Keep the non-obvious, project-specific points in mind:

- **CSS class prefix**: every class uses the `frontmatter-date-manager-` prefix, even when nested inside an already-prefixed parent.
- **Styling & colors**: use CSS classes + `toggleClass()` and Obsidian CSS variables (`var(--text-error)`, etc.) - never assign `element.style.*` or hardcode hex. Use `createEl()` / `createDiv()` / `createSpan()`, not `document.createElement()`.
- **Logical CSS properties (RTL-safe)**: `styles.css` ships RTL locales (`ar`, `fa`), so use **logical** properties - `padding-inline-start`/`-end`, `margin-inline-start`/`-end`, `border-inline-start`/`-end`, `text-align: start`/`end` - never new directional `*-left`/`*-right`/`text-align: left`/`right` (and avoid asymmetric `padding`/`margin` shorthands that bake in a left/right side). Diff-table cells holding LTR data (paths, dates, the `->`/`Δ` glyphs) carry `unicode-bidi: plaintext` so they read correctly inside an RTL line. lightningcss downlevels the logical properties to direction-aware `:lang()` rules at build, so `ar`/`fa` mirror automatically while LTR locales are unchanged. Verify any RTL-affecting CSS visually in a real RTL Obsidian locale (e2e runs English-only).
- **Headings**: in the settings tab, section headings come from the declarative `heading:` field on a `group` definition (imperative code elsewhere uses `new Setting(el).setHeading()`); never `createEl('h1'..'h6')` (heading elements inside `Modal` subclasses are fine); never show the plugin name as a top-level settings heading, and the first "general" section stays unheaded (1.13 style guide).
- **Window timers**: always `window.setTimeout` / `clearTimeout` / `setInterval` / `clearInterval` - never bare globals, never `activeWindow.*`. Timer IDs are window-scoped and `registerInterval()` cleans up on the main window, so the `obsidianmd/prefer-window-timers` rule rejects `activeWindow.*`. The bare `setTimeout(resolve, 0)` inside `new Promise(...)` must also be `window.setTimeout`.
- **Console**: the project routes ALL logging through `plugin.log()` / `plugin.logError()` (gated behind `__DEV_MODE__`); no raw `console.*` in production paths. ESLint's `no-console` would still permit `warn`/`error`/`debug`, but the project convention is stricter.
- **Sentence case**: all UI text (`setName`/`setDesc`/`setText`/`setPlaceholder`/`setButtonText`) in sentence case; avoid proper nouns (keep lowercase if unavoidable, e.g. "daily notes").
- **User-facing naming**: write every visible string (names, descriptions, buttons, modal headers, notices) so a non-technical Obsidian user understands it. Prefer Obsidian's own vocabulary - "property" (not "frontmatter key"), "date" / "date & time" (not "timestamp") - and keep implementation jargon (`inversion`, `ctime`/`mtime`) out of names and descriptions; describe out-of-order dates as "last-edited date earlier than the creation date". Where a mechanism term is unavoidable (e.g. "content hashing", "hash cache"), pair it with a plain-language explanation. Default property keys (`created`/`updated`/`viewed`/`updated_count`) and `HashTrackingMode` values (`body`/`frontmatter`/`both`) are identifiers - do not rename them.

Enforced by the linter/compiler - just satisfy `make lint`: no `any` (use `unknown` + narrowing), no floating promises (prefix `void`), `prefer-const`, `eqeqeq`, `??`/`??=` over `||`, `prefer-optional-chain` (no redundant `?.` on non-optional fields like `headerCreated` / `app.metadataCache`), `noUncheckedIndexedAccess` (`arr[i]` is `T | undefined`), and non-async `onunload()` (use `void this.method()` for async cleanup).

### Release

Release tags must be exact version numbers **without** `v` prefix (e.g. `1.0.0`, not `v1.0.0`). Obsidian requires this format to find release assets.

**A raised `minAppVersion` is a MINOR bump, not a major one** (decided at 1.3.0, which raised the floor `1.11.0 -> 1.13.0`). The release skill's changelog reference lists a raised `minAppVersion` among its breaking-change signals, so the literal rule would have produced `2.0.0`; that reading was rejected. `versions.json` exists precisely to map each plugin version to its floor, so Obsidian keeps serving the last compatible release (here `1.2.1`) to users on older app versions - nobody gets a broken install, they just stop receiving updates until they update Obsidian. Reserve major for an actual break in the plugin's own surface: a removed or renamed command / setting / default property key, or a changed default. Consequence for the changelog: no `## Breaking changes / Migration` section for a bare floor raise - state the new requirement as a Highlights bullet instead, spelling out that older-app users keep the previous release.

## Obsidian Community Plugin Review Requirements

This plugin targets the Obsidian community plugin store. All code changes must comply with the review process:

### Two-phase review
1. **Automated bot (scanner)**: Validates `manifest.json` and runs `eslint-plugin-obsidianmd` (recommended ruleset). It re-runs when you push a new release, but the cadence is not guaranteed (rescans can lag by days). Replicate locally with `make lint`, and keep the linter at its latest published version (the bot always runs latest - see the API section). **The scanner IGNORES this repo's `eslint.config.mts`** (so authors cannot loosen rules) and **wraps the ruleset with a "this rule cannot be disabled" check**: an `eslint-disable obsidianmd/<rule>` that passes a naive `make lint` still fails review with `Disabling '<rule>' is not allowed` (gating). It scans the WHOLE repo, including `e2e/` and other dirs this config's `globalIgnores` skips - so the local config is only a true superset if it adds that disable-restriction too (see below).
2. **Human reviewer**: Checks CSS scoping, code patterns, security, UX. Review can take weeks to months (the queue is heavily backlogged); a stale bot may close long-inactive PRs. Exact thresholds change - consult the submission requirements doc rather than relying on fixed numbers here.

### Replicate the scanner locally (no-restricted-disable)
Because the scanner forbids disabling its rules, `eslint.config.mts` mirrors that with `@eslint-community/eslint-comments/no-restricted-disable: ['error', 'obsidianmd/*']` in the `**/*.ts` block. This makes `make lint` a true superset: you **cannot** silence an `obsidianmd/*` finding with `eslint-disable` - fix the code instead (e.g. the marketing-screenshots helpers use `activeDocument`, not the global `document`, to satisfy `prefer-active-doc` and dodge `no-forbidden-elements` without a disable). The check that emits `Disabling '<rule>' is not allowed` is NOT part of `eslint-plugin-obsidianmd` (the published plugin has no such rule) - it lives only in the scanner's wrapper, which is why pinning/upgrading the plugin does not surface or fix it.

### Key ESLint rules (enforced by bot)
`eslint-plugin-obsidianmd` recommended config plus the overrides in `eslint.config.mts`; replicate the bot locally with `make lint`. The ones most likely to bite: `no-console` (route logging through `plugin.log()` / `plugin.logError()`), `no-explicit-any` (tests/mocks exempt), `no-floating-promises`, `settings-tab/no-manual-html-headings`, `ui/sentence-case`, `no-namespace` (use typed casts, not `declare namespace`).

### Capability disclosures (safety scorecard)
The new Obsidian Community automated review (2026) shows a **safety scorecard** with **capability disclosures** - informational labels for what a plugin's code *can* do (e.g. "Vault Enumeration", "Clipboard Access", "Network access", "File system access"). These are NOT policy violations and do NOT fail review: review fails only on Developer-Policy breaches, code-quality (eslint) issues, known vulnerabilities, and malware. Disclosures are **static** - triggered by the mere presence of an API in the source, regardless of when/whether it runs (the finding text cites the API names). A plugin can pass review with a top score while disclosing capabilities (e.g. Karpathy LLM Wiki discloses both vault enumeration and clipboard and still scores 95/100). The right response is least-access + honest justification, not chasing "zero disclosures". Decisions taken here:
- **Vault Enumeration is irreducible and kept.** It comes from `getMarkdownFiles()`, which every bulk operation needs; it cannot be removed without removing features. We keep it minimal (`getMarkdownFiles()` only, never `getFiles()` - attachments/binaries are never enumerated) and justify it in `README.md` → "Privacy & capabilities".
- **Clipboard Access was removed** by replacing the clipboard export with a local file download (`downloadPreviewAsFile`, see Destructive operation UX). `navigator.clipboard` no longer appears anywhere in `src/`. The download button is hidden on mobile via `Platform.isMobileApp` in `renderDownloadPreviewButton` (the `download` attribute no-ops silently in Capacitor; the full diff stays readable in the on-screen table). No clipboard fallback - a static scanner sees `navigator.clipboard` regardless of any platform guard, so even a mobile-only fallback would re-add the disclosure.
- **No network / no `child_process` / `vault.adapter` only for the plugin's own `hash-cache.json`** - so there is no Network or external File-system disclosure beyond the vault read inherent to the feature set.
- **Runtime "least-access" tweaks were rejected on purpose:** defaulting hash-cache auto-populate OFF would NOT remove any static disclosure and would regress safety (a cold cache makes the first sync-induced `modify` look like a real edit and spuriously stamp `updated` - the exact churn the hash cache prevents; see `shouldFileBeIgnored` cache-miss → `{ignored:false}`). Making rename/reformat respect filter rules also changes documented behavior without changing any disclosure.
- **Verify before release:** disclosures are confirmed via the Developer-Dashboard **preview scan** (run on a branch/tag/commit) - the exact tool that emits these labels. If the blob download ever triggers a new disclosure, fall back to keeping clipboard + the existing README justification.
